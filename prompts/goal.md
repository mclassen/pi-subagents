Work toward the supplied goal through a parent-controlled assess → plan → implement → verify cycle. Use existing mission actions, workflow state and ordinary subagents; do not add a runner or hand control to a child.

## Establish the goal

- If the invocation contains no concrete goal, ask for it and stop without creating a mission or changing files.
- Read applicable instructions, inspect repository status and the narrowest relevant source/evidence. State the goal, context, constraints and observable acceptance criteria. Ask only for blocking unknowns; do not invent requirements or silently reduce the requested scope.
- Default to a maximum of 8 iterations unless I specify a different positive integer. One iteration is one assess → plan → implement → verify cycle; increment the persisted count when its implementation/verification begins, not per worker, check, review, status update or cleanup action. No monetary or token budget is imposed by this template; do not invent one. State the selected iteration limit and proceed without asking me to confirm it. An explicit override in my request is approval for that limit, not a reason to pause.
- Use `subagent` with `action: "mission.list"` and `action: "mission.show"` to inspect an explicitly supplied mission or a possible existing match. Reuse a mission only when its identity, repository, objective and ownership are established; ask if ambiguous. Do not create a duplicate on continuation or reset its iteration count. Honor existing mission pause/stop settings unless I explicitly request resumption; do not silently override an existing restriction.
- Otherwise create one enclosing mission with `action: "mission.create"`, `mission: { title: <short goal>, objective: <full goal and acceptance criteria>, goal: true }` and `missionStatus: "active"`. Require the returned mission id before implementation. Record the iteration limit, iteration count, acceptance criteria and next action with `mission.update` in its summary; never invent an id or claim persistence succeeded after an error. Routine assessment, checkpoint recording and verified cleanup do not need separate confirmation unless applicable instructions require it.

## Assess and update the plan

- Assess the current code and evidence against the full goal. Name the next missing acceptance fact, then choose the smallest useful implementation or investigation that resolves it. Do not repeat unchanged checks merely because another pass started.
- Use repository-root `PLAN.md` as the canonical plan. Read an existing plan completely and preserve unrelated work; reconcile conflicts with me rather than replacing it. If it is missing, this goal request authorizes creating it after the initial assessment, not guessing among alternate plans.
- Update `PLAN.md` with the agreed goal, constraints, acceptance checks, current evidence, remaining work, dependencies and blockers. Mark partial work honestly. A passing subset does not complete the full goal.

## Implement and verify

- Keep diagnosis, shared decisions, integration and acceptance in the parent. Preserve the selected parent model and all existing authority, publication and destructive-operation restrictions. This prompt grants no new spending or publication authority.
- For plan implementation, launch 2–5 concurrent independent coding/test-writing workers through ordinary `subagent`, explicitly using `openai-codex/gpt-6.1-sol:medium` and real read/write/edit tools. Read-only reviewers, scouts and `fast_work` do not count as writers. If fewer than two safe useful lanes are ready, explain the concrete blocker and ask whether to rescope or proceed with fewer; do not silently implement alone or manufacture filler. The minimum need not persist after the queue naturally drains.
- Freeze only shared interfaces needed for independent work. Each worker owns named files/contracts in a distinct temporary workspace outside extension auto-discovery, with exact current inputs, applicable instructions, provisioned dependencies and a cold-start-complete brief. Maintain a compact ready/running/blocked queue and refill useful slots after accepted handoffs. Workers escalate new scope, product, architecture or shared-contract decisions.
- Discover tools/agents only when needed. For coordinated delegated work, use one top-level async workflow and attach the enclosing `missionId` to it; do not create a separate mission per child. Use native completion notifications rather than polling or waiting merely for a wake.
- In mission-linked workflows, persist the actual next parent action with `await state.set("nextReadyAction", <concrete action>)`. Also keep `PLAN.md` and the mission summary current at meaningful boundaries, including iteration limit and count, source/workspace identities, evidence paths, blockers and the next action. Do not create empty workflows solely to write a reminder.
- Inspect each handoff's actual diff, unexpected artifacts, focused checks and unresolved issues. Integrate accepted scoped changes into the original target and run the smallest authoritative regression plus required repository checks. Use an independent reviewer only for a named uncertainty that tests cannot settle or a required gate. An attestation, startup probe or continuation notice is not acceptance evidence.
- After verification, reassess the full acceptance criteria. If unmet but authorized work remains within the limits, update `PLAN.md` from the new evidence and begin the next iteration. Every retry must change the input or approach; stop if a changed attempt produces no new evidence or measurable progress. Do not loop on the same failure.

## Stop and recover honestly

- A failed or disappeared worker is not task success. Before recovery, report the exact failure and record run/status, repository/cwd/worktree/branch/ref, tracked and untracked partial edits, commands/evidence and outstanding acceptance checks. Preserve that work; partial edits remain unaccepted until parent inspection, integration and validation. Confirm the prior writer is terminal or demonstrably gone and establish exclusive ownership; missing notifications, quiet or `needs_attention` alone do not prove disappearance. Never replace a still-live writer or guess ownership.
- One bounded same-protocol recovery attempt for the failed lane is authorized without fresh user confirmation, within existing task/iteration limits and on the same approved model/provider/tools. Change the recovery input or approach based on failure evidence; never loop unchanged failure. Prefer resuming a proven eligible retained child using its exact ID. If unavailable or rejected, launch an explicitly labeled same-role replacement in a distinct isolated workspace with exact current inputs, preserved partial work and remaining checks. Record a clear ownership transfer and parent-captured recovery handoff in place of a missing final worker response. Recovery does not reset the iteration count or restrictions.
- Recoverable worker failures alone are not grounds to pause. If recovery fails again, no safe supported repair is available, ownership is uncertain, required tools/model/provider are unavailable, or the task/mission is paused, cancelled or out of iterations, checkpoint/report and ask for the smallest needed decision. No automatic destructive repair, spending, extra permissions, publication or execution-mode/model/provider fallback. Switching to local implementation, foreground or external CLI requires explicit approval.
- On an unresolved blocking decision, missing required evidence, permission failure, unrecoverable runtime failure, repeated recovery failure, no progress, or the iteration limit, persist the exact blocker, evidence and smallest needed decision in `PLAN.md` and the mission summary. Use `mission.update` with `missionUpdate: { status: "waiting", goal: { paused: true }, summary: <checkpoint and decision> }` (or `status: "needs_decision"` for a decision). Report the blocker immediately; no silent execution-mode, model or provider fallback.
- Before launching more work, check the mission's current goal status and persisted iteration count. Do not exceed the selected iteration limit or bypass an existing mission restriction. On my pause/cancel request, honor it and persist the stopping state. - On compaction/restart or a goal notice, read `mission.show`, canonical `PLAN.md` and linked-run status before deciding what is actually ready. Resume only a proven eligible retained child. Do not interpret the notice as fresh authority, progress or completion. Existing goal missions send continuation notices; they do not launch work, replan or guarantee autonomous completion. This template instructs the parent; it does not enforce future model compliance or prove recovery runtime reliability.
