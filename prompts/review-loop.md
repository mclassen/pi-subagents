description: Review/fix loop until clean
---

Run a parent-orchestrated review loop for the requested work.

Keep the full supplied code, branch, design, or plan as the target. Do not create, select, or sequence vertical slices, substitute a representative subset for the requested work, or invoke a slicing workflow automatically. An existing user-selected slice is valid input. Separate slice planning belongs to `/skill:vertical-slice` only when requested. Bounded fixes and delegation packets are execution details, not permission to redefine scope. Track incomplete requirements explicitly; a clean review of a subset does not complete the full target.

Use the `subagent` tool. Keep the parent session as the loop controller and final decision-maker. Child subagents must receive concrete role-specific tasks; they must not run subagents or manage the loop themselves unless the parent intentionally selected an explicit fanout agent whose builtin `tools` includes `subagent` for that assigned fanout.

Default to a maximum of 3 review rounds unless I specify a different cap. Count a review round each time fresh-context reviewers inspect the current diff after any parent or worker implementation/fix pass. Stop early when reviewers find no P0 findings, no P1 fixes worth doing now, and no approved P2 notes that should be handled in this loop. At the start of round 2 and every second round thereafter (4, 6, ...), reread the applicable global Pi `~/.pi/agent/AGENTS.md` and the target repository's nearest `AGENTS.override.md`/`AGENTS.md` from the exact repository/cwd under review. Treat this as an instruction-context refresh, not a reason to add a round; if a required file is missing or ambiguous, report it and follow the highest-authority instructions that are available.

Preserve the selected parent model. Sol 6.1 high is preferred for substantive parent reasoning; ordinary writers, test-writing, verification, review and helpers use Sol 6.1 medium. Explicitly launch coding/test-writing workers with model `openai-codex/gpt-6.1-sol:medium` (the suffix controls thinking), using real read/write/edit tools. Luna is only an explicitly selected cheap bounded read-only lookup, never implementation, review or verification. Astra medium is explicit-only. No model/provider substitution or silent fallback.

For plan implementation, read canonical repository-root `PLAN.md`; if missing or unclear, ask, never select another or overwrite it. Launch 2–5 concurrent independent coding/test-writing workers through ordinary `subagent` per applicable plan instructions. Read-only reviewers, scouts and `fast_work` do not count as writers. The parent resolves shared decisions and freezes only interfaces needed to release independent work. Approved bounded components with explicit ownership and independently testable outcomes qualify; they need not be mechanical or context-light. Workers solve local implementation details and escalate new product/architecture/scope/shared-contract decisions. Keep genuinely coupled/shared-state work and integration/acceptance in the parent. Being a Sol parent, or faster on one slice, is not a blanket reason to take all independent coding.

Record a compact ready/running/blocked queue: lane, owned files/contract, dependencies, workspace/base and acceptance gate. Start ready lanes promptly, up to five, and refill as useful independent work appears. If fewer than two safe useful lanes can be ready for `/implement-plan`, report the concrete blocker and ask whether to rescope or proceed with fewer; do not silently implement alone. Do not invent filler, overlapping tasks or fake concurrency. The minimum need not stay alive after the queue naturally drains. A single truly coupled follow-up defect needs no fabricated second task: the parent may fix it directly. `/implement-plan` remains a prompt-queuing command, not an automatic launcher or concurrency guarantee.

Every child gets a distinct temporary worktree/clone/snapshot with explicit cwd, outside extension auto-discovery, exact current inputs (including needed uncommitted source/config) and provisioned dependencies. Never run concurrent writers in the parent checkout or the same workspace: one writer per workspace, not one overall. Cold-start-complete brief: objective and plan requirements; workspace/base/current-source identity; applicable instructions, prior decisions and evidence; relevant source symbols/contracts/callers and adjacent consumers; owned files and prohibited edits; dependencies; acceptance and focused commands; patch/handoff location; stop/escalation rules. Fresh children do not inherit parent history. Missing inputs: stop, never invent.

If the current diff is already the target, start with review. Never pre-script worker → reviewers → next worker for uncertain work. Use `workflowScript` only when scripted implementation stages have approved bounded contracts and are independently ready; otherwise launch follow-ups after parent synthesis. For an initial workflowScript, pass `async: true` so the main chat is unblocked; do not set `clarify: true` unless I explicitly want the foreground clarify UI. Reuse identity-matched valid evidence; startup is established by the first useful isolated writer, not a routine probe. Startup/runtime failure or worker disappearance is not task success. Before recovery, report the exact failure and record run/status, repository/cwd/worktree/branch/ref, tracked and untracked partial edits, commands/evidence and outstanding acceptance checks. Preserve that work; partial edits remain unaccepted until parent inspection, integration and validation.

Confirm the prior writer is terminal or demonstrably gone and establish exclusive ownership before recovery; missing notifications, quiet or `needs_attention` alone do not prove disappearance. Never replace a still-live writer or guess ownership. One bounded same-protocol recovery attempt for the failed lane is authorized without fresh user confirmation, within existing task/iteration limits and on the same approved model/provider/tools. Change the recovery input or approach based on failure evidence; never loop unchanged failure. Prefer resuming a proven eligible retained child using its exact ID. If unavailable or rejected, launch an explicitly labeled same-role replacement in a distinct isolated workspace with exact current inputs, preserved partial work and remaining checks. Record a clear ownership transfer and parent-captured recovery handoff in place of a missing final worker response.

If recovery fails again, no safe supported repair is available, ownership is uncertain, required tools/model/provider are unavailable, or the task/mission is paused, cancelled or out of iterations, checkpoint/report and ask for the smallest needed decision. Do not reset iteration counts, review-round caps or existing restrictions. No automatic destructive repair, spending, extra permissions, publication or execution-mode/model/provider fallback; no silent fallback. Switching to local implementation, foreground or external CLI requires explicit approval. These instructions do not prove future model compliance or recovery runtime reliability.

As a conservative orchestration policy, do not set a hard `toolBudget` or tight `usageBudget` on implementation or fix workers. A default tool budget blocks read/search tools rather than mutation tools, and reported usage has no reservation model, so count or usage limits still do not measure delivery safety. Give each writer a narrow delivery slice and an outer elapsed deadline with enough margin. Before that deadline, request a checkpoint after the current tool returns with changed files, build/test state, remaining work, and commit or PR state. An elapsed timeout is not a mutation-safe boundary and must not be the checkpoint trigger.

For each review round that actually needs external review, launch at most one fresh-context `reviewer` for a simple review, or justified parallel reviewers for independent high-impact risks. Explicitly set each reviewer's model to `openai-codex/gpt-6.1-sol:medium`; never rely on a configured Luna default. Each runs in a distinct temporary read-only worktree/clone/snapshot containing the same exact integrated target diff. Record base/ref and focused diff identity; never share the parent checkout or another reviewer workspace. Reviewers must inspect the applicable global Pi `~/.pi/agent/AGENTS.md` and nearest target-repository instruction files, plus the current diff directly from files and commands, and receive the exact contracts, acceptance criteria, user constraints, and validation command. On rounds 2, 4, 6, and so on, explicitly include the refreshed instruction-file paths and any changed constraints in each reviewer packet. They must not rely on main conversation history or edit files.

Tell reviewers to filter on evidence, not severity. They should report only concrete current issues caused or made reachable by the target diff, with source proof, a test or repro, or a contract contradiction. Ask them to label findings P0/P1/P2 and end with `Merge verdict: BLOCK`, `Merge verdict: OK`, or `Merge verdict: OK with notes`. P0 blocks merge. P1 should be fixed before release. P2 is report-only. Use `blockers only` only for final pre-merge re-checks after P1/P2 findings are already captured, or for explicit emergency hotfix lanes.

Choose review angles from the actual change when external review is justified. Common angles are correctness/regressions, tests/validation, and simplicity/maintainability. Add security, performance, docs/API contracts, or user-flow validation only for independent high-impact risks. Prefer the parent review or one appropriately tiered, context-complete reviewer over reviewer fanout; do not prefer three reviewers by default.

After reviewers return, synthesize their feedback into:
- P0 blockers or scope/product/architecture decisions that need user approval;
- P1 fixes worth doing now;
- P2 report-only notes or optional improvements;
- feedback to ignore or defer, with a short reason.

For every implementation/fix iteration, record before choosing the next action:
- Implementation owner and owned files/contract: `parent` for genuinely coupled work or isolated `worker` lanes for independent components.
- Queue readiness/dependencies, workspace/base and acceptance gate; concrete blockers and any approved exception to the plan-writer minimum.
- Local implementation autonomy and shared decisions that require escalation.

Do not blindly apply every reviewer suggestion. If reviewers surface an unapproved product, scope, or architecture decision, pause and ask me before launching a fix worker.

Require actual scoped edits/patch, changed/new/generated files, command results with exit codes and unresolved issues. When an async implementation worker completes, the parent first checks diff/stat and unexpected artifacts, then integrates only accepted scoped changes into the original parent target and validates there before acceptance. Treat that integrated handoff as the transition into review, not final completion, unless I explicitly asked for worker-only work, review-only output, or to stop after implementation.

When there are fixes worth doing now and the workflow is implementation-authorized, the parent reclassifies the next work within the approved scope. Release useful independent components to isolated Sol 6.1 medium writers under the queue rules above; keep genuinely coupled fixes in the parent without artificial splitting. Require focused validation, changed files, scoped patch/handoff, commands with exit codes, evidence, surprises and anything left undone.

Parent owns cleanup for all settled lanes, including failed, cancelled and startup-failed runs. Preserve needed patches/handoffs/logs/recovery evidence outside temporary workspaces. Only after no active run needs the workspace and useful work is integrated or durably dispositioned, verify exact ownership/path and account for tracked/untracked/submodule contents. Delete only redundant agent-owned files, copied inputs and disposable outputs, then ordinary `git worktree remove`/`prune`, never `--force`. Safely preserved uncommitted agent changes alone do not require retaining unused copies. Never delete user work, uncertain ownership or unpreserved useful changes. Verify deletion and report retained paths/reasons; do not wait for push. Preserve cancellation, authority and no publication restrictions; this prompt grants no new runtime or publication authority.

After any parent or worker fix pass, run another review round only when it made material changes or addressed non-trivial findings. Do not keep looping for optional polish, speculative improvements, or findings already deferred by the parent.

For a targeted follow-up review, ask only three questions: whether the named finding was resolved, whether the fix introduced a new concrete defect in the fix blast radius, and whether prior P1/P2 notes still stand. End with a fix verdict and the merge verdict.

Stop and summarize when one of these is true:
- reviewers find no P0 blockers or P1 fixes worth doing now;
- remaining feedback is optional, speculative, or intentionally deferred;
- reviewers surface an unapproved decision that needs me;
- the max review-round cap is reached.

On completion, inspect the final diff yourself, run or confirm focused validation where appropriate, and summarize the loop: rounds run, fixes applied, validation, remaining deferred items, and why the loop stopped.
